# Getting Started

SCARline is a monorepo plus a command line tool. The tool is the entry point for
everything: it validates configuration, generates secrets, starts the Docker services
and the host processes, and reports what is healthy.

## The Shortest Path

```bash
npm install && scarline setup && scarline doctor && scarline start
```

`npm install` builds the CLI and links it globally. `setup` validates `config.yml`,
creates `.env` with strong random secrets, and creates `.runtime/`. `doctor` checks the
host for everything the stack needs. `start` brings the platform up.

Then open the Admin Panel at `http://localhost:5173` and sign in with the bootstrap
administrator. Full detail is in [Install And First Run](/getting-started/install).

## What You Need

| Requirement | Version | Why |
| --- | --- | --- |
| Node.js | 22 or newer | CLI, CoreAPI, Sim-Bridge, Admin Panel, Overlay Web |
| npm | 10 or newer | Workspace installs |
| Docker + Compose v2 | current | Every containerised service |
| Python | 3.12 or newer | IO Client, only when it runs on the host |
| CARLA | 0.9.16 | Optional; Linux or Windows host only |

`scarline doctor` checks all of these and tells you which one is missing.

## The Mental Model

- **`config.yml`** is the only place non-secret configuration lives. It is read by the
  CLI, CoreAPI, and Sim-Bridge. Nothing in the UI edits it.
- **`.env`** is the only place secrets live. It is generated by `scarline setup`,
  excluded from Git, and never printed.
- **`.runtime/`** holds everything generated at run time: database volume, logs, command
  journals, exports, process records. It is not tracked by Git.
- **The CLI owns process lifecycle.** The Admin Panel shows platform state; it does not
  start or stop anything.
- **CoreAPI owns persisted state.** Every other service reaches it through REST,
  WebSocket, or RabbitMQ — never through another service's database.
