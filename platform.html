Why SCARline

Your study, not the plumbing

Evaluating an in-vehicle interface means juggling driving simulation software, interaction design and user study methodology at the same time — a steep learning curve for anyone without a deep technical background.

SCARline abstracts that complexity into one system. You don't need to know how the simulator works internally, only what you are testing and how. You still design the interaction; the platform removes everything between your idea and a running study.

One pipeline

From idea to dataset

One system covers the full research workflow. Each step lives in its own tab of the study workspace.

  1. Step 1

    Study

    Design

    Create a study, add anonymised participants and define conditions — the experimental variants you want to compare.

  2. Step 2

    Simulator & sensors

    Configure

    Per condition, pick map, weather, vehicle and traffic, and attach the sensors you want to record.

  3. Step 3

    Participant view

    Compose

    Drag widgets onto the participant's displays, size them and bind them to live data.

  4. Step 4

    Readiness

    Check

    Readiness checks confirm that everything required is configured and connected, and link straight to the fix.

  5. Step 5

    Active study

    Run

    Start sessions, move through conditions, trigger widgets and take notes while watching live data.

  6. Step 6

    Logs & exports

    Review

    Browse the full event stream and export pseudonymised CSV or JSON archives for analysis.

Capabilities

What the platform does for you

  • Condition-based study design

    Simulator settings, sensors, layouts and trigger rules all belong to a condition. Set one variant up properly, then clone it as a template for the next.

  • Drag-and-drop participant view

    Place widgets on a canvas, assign each one to a display, and preview the whole layout with sample data before a participant ever sits down.

  • Ready-made & custom widgets

    Start from the widget library or build your own from plain HTML, Tailwind CSS and a JSON manifest — no framework, no build step.

  • Simulator integration

    Drive CARLA with a steering wheel, autopilot or external control, or use the mock simulator to develop and test without a GPU.

  • Sensors & physiological data

    Record steering input, heart rate, ECG, camera-based gaze and blink data alongside the drive, each at its own sample rate.

  • Trigger rules

    Make widgets react to the drive: show, hide or highlight them when speed, distance or any other value crosses the threshold you define.

  • Live session control

    Watch telemetry, events, sensor health and widget data in real time. Pause, advance to the next condition, trigger widgets or add notes on the fly.

  • Logs & privacy-aware exports

    Every event is logged per session. Export by study, participant or session as CSV or JSON, pseudonymised by default.

  • Reproducible by design

    When a session starts, its configuration is frozen as a snapshot. Later edits can never change what a completed session actually ran.

An auditable session lifecycle

Every session moves through the same states. Each transition is a command that the simulator and sensor services must confirm before it takes effect, so a session never ends up half-started.

  1. Created
  2. Ready
  3. Running ⇄ Paused
  4. Completed

Sessions can also be aborted with a reason, or fail automatically if a required device or the simulator drops out.

Widgets

The interface the driver actually sees

A widget is one piece of in-car interface: a speed readout, a heart-rate panel, an incoming-call card. Widgets are connected to the simulation, so they change with what is happening on the road. Every widget has a resting state and a triggered state.

Build your own

Need something the library doesn't have? A widget is just a folder of three plain web files: no framework, no build step. If you can sketch it, you can build it, or hand the sketch to a teammate or an AI assistant.

  • index.html

    What the widget looks like, styled with Tailwind CSS.

  • widget.json

    Its name, size and the live data it listens to.

  • <widget-id>.png

    A preview image for the layout editor.

Under the hood

Built so your data doesn't get lost

The simulator never talks to your widgets directly. Every value travels through a small chain of services connected by a message queue, so one part can restart without taking the study down with it.

  • One command

    A single CLI checks your setup, starts every service and tells you whether everything is healthy.

  • Nothing half-starts

    Simulator and sensors must confirm every start, pause and condition change. If they don't, the session stops cleanly.

  • Never a stale number

    When data stops arriving, a widget shows a dash instead of an old value, and the operator sees why.

Get started

Running in four commands

SCARline is open source. Clone it, install it and start it with the mock simulator and synthetic sensors to try a complete study on your own laptop, no driving rig or GPU required.

  • Node.js 22+
  • Docker
  • CARLA 0.9.16 (optional)

Terminal

git clone https://github.com/tugcanonbas/SCARline.git
cd SCARline && npm install
scarline setup
scarline start --simulator mock --mock-io
