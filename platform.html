The platform

From first idea to clean dataset

SCARline covers every stage of a driving simulator study in one workspace. Here is what it does for you at each one, from setting up conditions to exporting the data.

  1. Design
  2. Compose
  3. Check
  4. Run
  5. Review

Design

Every variant, fully defined

Create a study, add anonymised participants and define the conditions you want to compare. Each condition carries its own simulator settings, sensors, layout and trigger rules.

  • Condition-based study design

    Set one variant up properly, then clone it as a template for the next.

  • A simulator setup per condition

    Pick map, weather, ego vehicle, traffic and pedestrians for each condition.

  • Sensors per condition

    Attach the sensors you want to record, each at its own sample rate.

Compose

Build the interface the driver sees

Drag widgets onto the participant's displays, size them and bind them to live data from the drive.

  • Drag-and-drop participant view

    Place widgets on a canvas, assign each one to a display, and preview the whole layout with sample data before a participant ever sits down.

  • Trigger rules

    Show, hide or highlight widgets when speed, distance or any other value crosses the threshold you define.

  • Ready-made & custom widgets

    Start from the widget library or build your own from plain HTML, Tailwind CSS and a JSON manifest.

Check

Know it works before anyone sits down

Readiness checks confirm that everything required is configured and connected, and link straight to the fix.

  • Readiness checklist

    See exactly what's missing before a study can go live, one click away from the setting that fixes it.

  • Required devices

    Mark a device as required and the study can't go live until it is connected.

  • Rehearse without a lab

    Run the whole study with the mock simulator and synthetic sensors on any laptop, no driving rig or GPU required.

Run

Stay in control during every session

Start sessions, move through conditions, trigger widgets and take notes while watching live data.

  • Live session view

    Watch telemetry, events, sensor health and widget data in real time.

  • Operator controls

    Pause, advance to the next condition, trigger widgets or add notes on the fly.

  • A clear session lifecycle

    Every session moves from Created to Ready, Running or Paused, and Completed. It can be aborted with a reason, and fails automatically if a required device or the simulator drops out.

Review

Leave with a clean dataset

Browse the full event stream and export pseudonymised CSV or JSON archives for analysis.

  • Every event logged

    Each session keeps its complete event stream, ready to browse.

  • Privacy-aware exports

    Export by study, participant or session as CSV or JSON, pseudonymised by default.

  • Reproducible by design

    When a session starts, its configuration is frozen as a snapshot. Later edits can never change what a completed session actually ran.

Widgets

The interface the driver actually sees

A widget is one piece of in-car interface: a speed readout, a heart-rate panel, an incoming-call card. Widgets are connected to the simulation, so they change with what is happening on the road. Every widget has a resting state and a triggered state.

Build your own

Need something the library doesn't have? A widget is just a folder of three plain web files: no framework, no build step. If you can sketch it, you can build it, or hand the sketch to a teammate or an AI assistant.

  • index.html

    What the widget looks like, styled with Tailwind CSS.

  • widget.json

    Its name, size and the live data it listens to.

  • <widget-id>.png

    A preview image for the layout editor.

Under the hood

Built so your data doesn't get lost

The simulator never talks to your widgets directly. Every value travels through a small chain of services connected by a message queue, so one part can restart without taking the study down with it.

  • One command

    A single CLI checks your setup, starts every service and tells you whether everything is healthy.

  • Nothing half-starts

    Simulator and sensors must confirm every start, pause and condition change. If they don't, the session stops cleanly.

  • Never a stale number

    When data stops arriving, a widget shows a dash instead of an old value, and the operator sees why.
