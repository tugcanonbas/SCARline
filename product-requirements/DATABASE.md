## 1. Overview

[PostgreSQL](https://www.postgresql.org) is the **single data store** for all SCARline platform data. All metadata, configuration, session data, event logs, and telemetry streams are stored in PostgreSQL. There is no separate filesystem-based storage — the database is the sole source of truth for all data generated by the platform.

This design ensures:
- **Reliability**: ACID-compliant transactions protect study data integrity
- **Queryability**: All data is accessible through SQL for analysis and export
- **Simplicity**: Single data layer reduces operational complexity
- **Backup**: Standard PostgreSQL backup tools cover all platform data

## 3. JSONB Usage Strategy

SCARline uses JSONB columns for flexible, schema-evolving data. This approach is used when:

- The data structure varies between entries (e.g., sensor-specific metadata, CARLA configuration parameters)
- The data is primarily read/written as a whole unit rather than queried field-by-field
- Forward compatibility is needed (new fields can be added without schema migrations)

### JSONB Column Guidelines

| Use Case | Column Name Convention | Example |
|----------|----------------------|---------|
| Widget bindings configuration | `bindings_config` | `{"speed": {"source": "vehicle.speed", "unit": "km/h"}}` |
| CARLA configuration parameters | `parameters` | `{"weather": {"cloudiness": 80, "precipitation": 50}}` |
| Sensor metadata | `metadata` | `{"sample_rate": 60, "calibration": {...}}` |
| Event/telemetry payloads | `payload` | `{"vehicle": {"speed": 45.2, "position": {...}}}` |
| Widget trigger rules | `trigger_rules` | `[{"condition": "speed > 30", "action": "show"}]` |

### JSONB Indexing

For JSONB columns that are frequently queried, GIN indexes should be created:

```sql
CREATE INDEX idx_session_events_payload ON session_events USING GIN (payload);
CREATE INDEX idx_carla_configs_parameters ON carla_configurations USING GIN (parameters);
```

## 4. Performance Requirements

### Real-Time Constraints

The database must not degrade real-time widget rendering or event processing:

| Operation | Target Latency | Notes |
|-----------|---------------|-------|
| Event write (single) | < 5ms | Session events, telemetry snapshots |
| Batch event write | < 50ms | Bulk ingest of sensor/telemetry data |
| Study/session metadata read | < 10ms | Dashboard, study overview |
| Widget binding data read | < 5ms | Real-time widget data fetch |
| Session log query (paginated) | < 100ms | Log browser with pagination |
| Export data aggregation | < 5s | Full study/session data export (async) |

### Write Throughput

During active study sessions, the database must handle:

- Simulator telemetry: up to **20 events/second** per session (at 20 FPS simulation tick)
- Sensor data: up to **60 events/second** per sensor (e.g., 60 Hz eye tracker)
- Widget trigger events: sporadic, < 10 events/second
- Session lifecycle events: sporadic, < 1 event/second

**Estimated peak write load**: ~200 events/second during an active session with multiple sensors.

### Connection Pooling

CoreAPI should use a connection pool to manage database connections:

| Parameter | Recommended Value |
|-----------|------------------|
| `min` | 2 |
| `max` | 20 |
| `idleTimeoutMillis` | 30000 |
| `connectionTimeoutMillis` | 5000 |

## 5. Schema Management

### Authoritative Schema

The database schema is defined in a single authoritative file:

```
infra/database/schema.sql
```

This file is the source of truth for the database structure. The `schema-bootstrap` Docker container applies this schema on startup.

### Schema Application

- On first run: the full schema is applied
- On subsequent runs: the schema is applied idempotently (using `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, etc.)
- No migration framework is required for the initial version
- When the schema evolves, the authoritative file is updated and reapplied

### Development Utilities

| Script | Purpose |
|--------|---------|
| `infra/database/schema.sql` | Authoritative schema definition |
| `infra/database/scripts/apply_schema.sh` | Apply schema to running database |
| `infra/database/scripts/reset_dev.sh` | Drop and recreate database (development only) |
| `infra/database/seed/seed_dev.sql` | Insert development seed data |

## 6. Backup and Restore

### Backup Requirements

- Full database backups must be supported via standard `pg_dump`
- Researchers must be able to export individual study data through the Admin Panel (handled by CoreAPI export functionality)
- Backup/restore should not require stopping the platform

### Recommended Backup Strategy

```bash
# Full backup
pg_dump -h localhost -U scarline -F c -b -v -f scarline_backup.dump scarline

# Restore
pg_restore -h localhost -U scarline -d scarline -v scarline_backup.dump
```

## 7. Data Retention

| Data Type | Retention Policy |
|-----------|-----------------|
| Study metadata | Permanent (until explicitly deleted) |
| Session events and telemetry | Permanent (critical research data) |
| System configuration | Permanent |
| Export job records | 90 days after completion |
| Authentication tokens | Until expiration or explicit revocation |

> **Important**: Study data (sessions, events, participants) must never be automatically deleted. Researchers rely on historical data for longitudinal analysis.
