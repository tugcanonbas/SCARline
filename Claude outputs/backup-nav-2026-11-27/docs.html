Getting started

Install & first run

From a clean machine to a running platform and a signed-in administrator.

Requirements

  • Node.js 22+
  • npm 10+
  • Docker with Docker Compose
  • Git (optional)
  • CARLA 0.9.16 (optional, Linux or Windows)
  • Python 3.12+ (only for the host-run IO Client)

1 Get the code

With Git:

git clone https://github.com/tugcanonbas/SCARline.git

Without Git: on the GitHub repository, choose Code → Download ZIP and unzip the folder.

2 Install the workspace

cd SCARline
npm install

npm install installs the workspaces, builds the shared contracts and the CLI, builds the desktop overlay and links the scarline command globally. Check it with scarline --help. If the command isn't found, npm's global folder isn't on your PATH; you can run the CLI without the link as npm run dev:cli -- --help.

3 Run setup

scarline setup

Setup is safe to run repeatedly. It:

  • validates config.yml against the shared schema,
  • creates or completes .env, generating any missing secret without overwriting or printing existing ones,
  • creates the .runtime/ folder,
  • creates the IO Client's Python environment when the IO Client is configured to run on the host.

4 Check the host

scarline doctor

A read-only check of Node.js, npm, Docker and its daemon, config.yml, secrets, the runtime folder, free ports, the desktop overlay build and, if autostart is on, the CARLA executable. Each check reports PASS, WARN or FAIL. A port reported as WARN is usually a SCARline service that is already running.

5 Start the platform

scarline start --simulator mock --mock-io

This starts the Docker services, waits until they are healthy, then starts the processes that run on the host (desktop overlay, and the IO Client when it runs on the host) and prints a status table.

CommandResult
scarline startUses simulator.default when simulator.autostart is true; otherwise starts no simulator
--simulator mockStarts the mock simulator
--simulator carlaStarts the CARLA server on the host and the CARLA adapter
--no-simForces the mock simulator, for hosts that can't run CARLA
--mock-ioEnables the synthetic sensor suite

No GPU or driving hardware? --simulator mock --mock-io runs the whole platform with simulated driving and sensor data. CARLA needs a Linux or Windows host; on macOS use --no-sim. To switch simulators, run scarline stop first.

6 Sign in

Open the SCARline Hub at localhost:5173 and sign in as admin with the password scarline. You'll be asked to set a new password of at least 12 characters before anything else is reachable, then sign in again.

The first password is not random. It is copied from .env.example and only exists to create the first administrator. Change BOOTSTRAP_ADMIN_PASSWORD in .env before exposing the platform beyond your own machine.

7 Stop

scarline stop

Stops the host processes and the Docker services. Study data under .runtime/ is kept, so the database survives a stop and start.

CLI commands

The scarline command finds the repository by itself, so you can run it from any subfolder. scarline <command> --help prints the usage of each command.

CommandWhat it does
scarline setupValidates config.yml, generates secrets and prepares the runtime folder. Safe to run repeatedly.
scarline doctorRead-only diagnostics of the host and configuration. Exits non-zero if any check fails.
scarline startStarts the platform. Options: --simulator carla|mock, --no-sim, --mock-io. Re-running it on a healthy stack is safe.
scarline statusShows each service and host process and the overall state: running, starting, stopped or degraded.
scarline stopStops the platform while keeping all study data.
scarline restart, logsNot implemented yet. Use scarline stop && scarline start and the commands below.

Logs

docker compose -p scarline logs -f core-api

Host-process logs are written to .runtime/logs/: desktop-overlay.log, io-client.log, carla-server.log and carla-driver.log.

Troubleshooting

Start with scarline doctor and scarline status; they answer most questions. Error output has secrets removed, so it is safe to paste into an issue.

Startup fails

MessageFix
Invalid config.yml: …The message names the key; compare it with Configuration.
.env does not existRun scarline setup.
A secret is too shortDelete that line from .env and re-run scarline setup.
Compose could not start the infrastructureA service failed its health check: docker compose -p scarline logs <service>.
Simulator is already runningscarline stop, then start with the other simulator.
CARLA requires Linux or WindowsUse scarline start --no-sim.

Sign-in or access fails

SymptomCause
Every page redirects to /startupThe Core API isn't ready yet: PostgreSQL, RabbitMQ or the admin account is still starting.
Stuck on /change-passwordSet a new password of at least 12 characters.
403 STUDY_ACCESS_DENIEDThe account isn't a member of that study. Add it to the study's users.
403 ORIGIN_DENIED at loginThe browser address is missing from api.allowed_origins in config.yml.

Widgets or overlay misbehave

SymptomWhere to look
No participant windows openIs the desktop overlay running? Check scarline status, or start the session in browser renderer mode.
Widget shows — for every valueThe data source isn't streaming. Check Active Study → Widget data sources.
WIDGET_CATALOGUE_INVALIDA widget.json failed validation; the response lists the problems.
Window on the wrong screenThe saved display no longer exists. Reassign it in Participant View.

Simulator or sensors

  • SIMULATOR_UNAVAILABLE in the readiness checks means Sim-Bridge isn't reporting a heartbeat (status goes stale after 15 seconds).
  • missingSimulatorCapabilities means Sim-Bridge is up but no adapter of the configured type has registered. Check that you started the right simulator.
  • REQUIRED_SENSOR_UNAVAILABLE means a device marked required isn't connected, or the IO Client isn't reporting.

Concepts

Architecture

The scarline CLI validates the configuration, starts the Docker services and the processes that run on the host machine, and reports their health. Everything else — study design, live sessions, participant displays, simulator and sensor integration, data export — runs on top of that stack.

Design principles

  • Services talk through a queue

    Backend components exchange commands and events over RabbitMQ instead of calling each other directly. A simulator or overlay can restart without disturbing study data.

  • One owner for study data

    Only the Core API writes to the database. A state change and the message announcing it are saved together, so neither can get lost.

  • Configuration is snapshotted

    When a session becomes ready, each condition's simulator, device and sensor settings are frozen. Completed sessions stay reproducible.

  • Transitions are confirmed

    Starting, pausing or advancing a session is a command the simulator and sensor services must acknowledge. If they don't in time, the session fails cleanly instead of half-starting.

  • Widgets are plain web files

    Static HTML, CSS and vanilla JavaScript, with no framework and no build step. New widgets are picked up without rebuilding anything.

  • Roles are enforced on the server

    Admins, researchers, operators and observers each see and do only what their role allows, checked by the server rather than hidden in the interface.

Components

ComponentResponsibility
scarline CLIValidates configuration, generates secrets, starts and stops the stack, runs diagnostics.
SCARline HubThe web app for researchers and operators (the Admin Panel): study setup, layout editor, live operation, logs and exports.

Concepts

Data flow

The simulator never talks to your widget directly. Follow a single speed reading on its way to the participant's display.

  1. SimulatorThe vehicle reaches 80 km/h in CARLA.
  2. Sim-BridgeTranslates raw simulator state into messages the rest of the system understands.
  3. RabbitMQHolds the message in a queue until something is ready to pick it up.
  4. Core APIConsumes it and packages it into the data field your widget is listening for.
  5. OverlayReceives it over an always-open WebSocket and updates the widget on screen.

Why a queue in the middle?

RabbitMQ acts as a buffer rather than a direct handoff. The simulator side and the widget side never depend on each other being up at the same moment, and a component that restarts mid-command replays its recorded result instead of running it twice.

Fresh, not stale

Live values reach each widget at most ten times per second. Each binding declares how long a value stays fresh; when data stops arriving, the widget shows — instead of an old number, and the operator can see why in the live session view.

Steering input takes a separate, faster path: the IO Client publishes throttle, steer and brake straight to Sim-Bridge, bypassing the durable event pipeline, because control input can't tolerate that latency.

Concepts

Studies & sessions

Two state machines run side by side: a study moves through design and execution phases, and each session runs one or more conditions in a fixed order.

Study status

StatusConfiguration editableSessions can be created
draftYesNo
configuredYesYes
readyNoYes
runningNoYes
completedNoNo
archivedNoNo

Moving to ready re-runs the readiness checks and is refused if any blocking check fails. A study becomes running automatically when its first session starts. Configuration also locks as soon as any session is ready, running or paused.

Session status

  1. Created
  2. Ready
  3. Running ⇄ Paused
  4. Completed

Any session that isn't finished can also be aborted (a reason is required) or failed. completed, aborted and failed are final.

ActionEffect
readyFreezes each queued condition's configuration as a snapshot.
startActivates the first condition and opens the participant's windows.
pause / resumePauses and resumes the session and its active condition.
advanceCompletes the active condition and starts the next one; the session stays running.
completeCompletes the active condition and marks the remaining ones skipped.
abort / failEnds the session and closes all participant windows.

How a command runs

  1. The Hub sends the action; the Core API checks the transition is allowed and queues a command with a deadline.
  2. The command goes to Sim-Bridge and, when devices are configured, to the IO Client. start and advance carry the snapshot of the next condition.
  3. Each component acknowledges with completed or failed.
  4. Once every required acknowledgement is in, the Core API applies the change and opens or closes participant windows.
  5. If the deadline passes first, the command times out and the session fails.

Only one command can be in flight per session. The deadline is api.command_timeout_seconds in config.yml.

Concepts

Accounts & roles

There is no onboarding wizard. When the database has no users, the Core API creates the first administrator from bootstrap.admin_username in config.yml and BOOTSTRAP_ADMIN_PASSWORD in .env. Further accounts are created under Settings → User Accounts.

RoleCan do
adminSystem administration and every study, without needing membership
researcherDesign and operate studies they are a member of; queue exports
operatorOperate sessions on studies they are a member of; add notes and trigger widgets
observerRead the studies, sessions and events they have access to

Roles add up, so one account can hold several; an account created without roles is an observer. Roles say what someone may do, study membership says which studies: an operator who can't see a study usually needs to be added to it, not a different role. Every new or reset account must set its own password at first sign-in.

Building

Widgets

A widget is a folder of static files inside widgets/components/, for example widgets/components/calendar/. There is no framework and no bundler; a shared runtime script handles data binding and interactions for you.

  • index.html

    The widget's visual structure, styled with Tailwind CSS classes.

  • widget.json

    The manifest: name, category, size and, most importantly, the data bindings the widget expects.

  • <widget-id>.png

    A preview image shown in the layout editor, so the widget is recognisable without loading it live.

The manifest

FieldMeaning
idMust match the folder name
name, description, versionShown in the widget catalogue
categoryGroups the catalogue, e.g. driving, health, communication, study, general
entryThe HTML file to load; defaults to index.html
bindingsThe data the widget receives (see below)
actionsThe actions the widget can send out
ui.minSize, ui.preferredSizeWidth and height enforced by the layout editor
windowframe (none or default) and transparent for overlay use

Receiving live data

Give an element a data-bind attribute and declare the same key in widget.json. The runtime fills the element with live values as they arrive.

index.html

<script src="../../widget-runtime.js"></script>

<div data-scarline-widget-root>
  <span data-bind="vehicle.speed"
        data-format="number"
        data-decimals="0">—</span>
  <span data-bind="vehicle.speed_unit">km/h</span>
</div>

widget.json

"bindings": {
  "vehicle.speed": {
    "type": "number",
    "unit": "km/h",
    "source": "live",
    "staleAfterMs": 5000,
    "preview": 132
  },
  "vehicle.speed_unit": {
    "type": "string",
    "default": "km/h",
    "source": "presentation"
  }
}
Binding fieldMeaning
typenumber, string, boolean, object or array
sourcelive from the running session, study from the condition's configuration, or presentation for display settings such as a unit label
previewExample value used when you preview the widget in the layout editor
defaultValue used when nothing else is configured
staleAfterMsHow long a value stays fresh: about 5 s for continuous readings, 2 s for ECG, 60 s for blood pressure
unit, label, description, requiredPresentation metadata, and whether the widget needs the value

default and preview are checked against type, so a mistake fails validation instead of showing up as NaN. Use — as the initial content of every value element: missing, stale or disconnected values reset to it.

Declarative attributes

AttributeEffect
data-scarline-widget-rootThe element the runtime applies the visual state to
data-bindBinding key for this element
data-format="number" + data-decimalsNumeric formatting
data-bind-attrWrite the value to this attribute instead of the text
data-bind-class, data-bind-class-falseToggle classes on truthy or falsy values
data-bind-style, data-style-unitWrite the value to a CSS property, with an optional unit
data-bind-label-true, data-bind-label-falseSwap label text on a boolean
data-chart, data-chart-window, …Draw a time series, e.g. ECG or heart rate
data-actionSend this action when clicked

Sending actions out

Buttons and other controls report interactions through data-action. Most widgets only display data, but for anything the attributes can't express there is a small JavaScript API.

Declarative

<button type="button" data-action="call.decline">
  Decline
</button>

Runtime API

<script type="module">
  const { SCARline } = window;

  SCARline.onBinding("vitals.heart_rate", (v) => {
    document.querySelector("#bpm").textContent = v ?? "—";
  });

  document.querySelector("#mute")
    .addEventListener("click", () =>
      SCARline.send("call.mute", { muted: true }));

  SCARline.ready();
</script>
Runtime APIPurpose
ready()Signal that the widget has mounted; call it last
getBinding(key)Current value of a binding
onBinding(key, fn)Subscribe to a binding; returns an unsubscribe function
getState(), onStateChange(fn)Visibility: visible, hidden or highlighted
onTrigger(fn)Trigger and interaction-result events
getMetadata()The widget's manifest
send(action, payload)Send a declared action

Widgets run in a sandboxed frame with no other access to the page, the Core API or cookies. Actions are round trips: the control is disabled until the result arrives, and a retry never applies the same action twice.

From idea to running widget

  1. CreateAdd a folder in widgets/components/ named after your widget.
  2. DesignDraft index.html with Tailwind classes and data-bind attributes.
  3. DeclareList the bindings and actions in widget.json, plus a preview image.
  4. RefreshRun npm run widgets:build-css if you used new Tailwind classes, then refresh the catalogue in Participant View.
  5. PreviewPlace it in a layout and launch a preview with your preview values.
  6. TestCheck it in a real session with live data and run npm run test:widgets.

Guidelines

  • Keep the widget legible at its minimum size; it is read on a driving display, in motion.
  • Never fabricate a value. An absent reading is —, not 0.
  • Label simulated data as simulated; the synthetic sensor suite is a test signal.
  • Don't derive clinical claims from a signal: a BPM value is a number, not a diagnosis.

No coding background? Sketch the widget and its resting and triggered states, then let a teammate or an AI assistant turn it into the three files above.

Building

Simulators

Simulators connect through Sim-Bridge, the only component they talk to. It registers simulator adapters, turns session commands into adapter messages, journals every result so a restart never runs a command twice, and limits how fast telemetry is published. An adapter can disconnect, crash or be swapped without touching study or session records.

CARLA 0.9.16

  • Runs on the host operating system (Linux or Windows); only the adapter runs in Docker.
  • scarline start --simulator carla starts the server, or attaches to one that is already running.
  • Synchronous mode with a fixed 0.05 s step, so runs are reproducible.
  • A keyboard driver is started alongside for manual control.

Mock simulator

  • Deterministic telemetry (smooth speed, throttle and steering) at up to 20 Hz.
  • Runs on any laptop, no GPU required.
  • The right choice for widget development, automated tests and rehearsing a study.
  • If both are connected, CARLA takes priority.

CARLA settings per condition

GroupSettings
WorldMap, weather preset or custom weather (clouds, precipitation, wind), sun altitude
Ego vehicleVehicle blueprint and control mode: io (steering wheel), autopilot or external
DeterminismSynchronous mode, 0.05 s fixed step, random seed
TrafficNumber of other vehicles, speed difference, optional speed-limit override
PedestriansNumber of pedestrians
SpectatorCamera position and orientation
RecordingOn or off, and a relative output folder
SensorsUp to 100 CARLA sensor.* blueprints with attributes and position

If an adapter stops sending heartbeats it is treated as disconnected. Its session is held for a short grace period so a brief reconnect goes unnoticed; after that the session fails.

Building

Sensors

The IO Client is a Python service that owns every sensor. It discovers hardware, starts the drivers a session needs and sends samples in batches over RabbitMQ. It runs either in Docker or directly on the host; host mode is what you need when the hardware is plugged into that machine (services.io_client.runtime: host).

Shipped drivers

DriverDeviceChannels
logitech_g29Steering wheel and pedals (Linux)Controls, 100 Hz
heart_rateHeart rate monitorHeart rate in bpm, 1 Hz
ecgSiFi Labs ECGECG in mV, 500 Hz
cameraCamera and face featuresVideo 30 Hz, blink 10 Hz, gaze 10 Hz
mockSynthetic sensor suiteSteering, heart rate, ECG, blood pressure, SpO₂, respiration, eye tracking

Hardware drivers need an optional Python dependency. Without it the driver appears in the catalogue but can't connect. Everything from the synthetic suite is labelled as simulated.

Devices in a study

Devices are registered globally, either by an administrator under Settings → Devices or automatically when the IO Client discovers hardware. You then attach a device to a condition and choose which of its channels to record.

  • Mark a device required and the study can't go live until it is connected.
  • The on disconnect policy decides what happens mid-session: fail stops the session (the default for required devices), continue keeps it running and records the loss.
  • Each channel samples at its own rate; slow channels such as heart rate are sent immediately rather than waiting for a batch.

Reference

Configuration

config.yml in the repository root holds all non-secret configuration; secrets live in .env, which scarline setup generates. The schema is strict, so an unknown key is an error. Nothing reloads it at run time.

SectionWhat it controls
bootstrapUsername of the first administrator
apiAllowed browser origins, command timeout, token lifetimes, and the widget, sensor and export folders
platformEnvironment, Core API port, runtime folder, start-up and shutdown timeouts
dockerCompose file and project name
database, rabbitmqHosts, ports and users (passwords come from .env)
sim_bridgePort, adapter timeouts, heartbeat and reconnect windows, telemetry rate limit
simulatorDefault simulator, autostart, CARLA path and quality, mock telemetry rate
servicesWhich services run, their ports, and whether the IO Client runs in docker or on the host
loggingLog level and log folder

Changing configuration safely

# 1. edit config.yml, then
scarline doctor
scarline stop && scarline start

The current values are visible read-only in the Hub under Settings → System Settings.
